Genesis — What AOTU taught us

AOTU reached v0.0.8 with 53 known bug items, 3 databases, a dual-summary pipeline, two tool-execution paths, and a frontend with competing stores. The v3 refactor plan fixed most of this. AOTUS inherits those fixes at birth.

Keep from AOTU v3
  • • InteractionRuntime as single state owner
  • • ChatService as stateless functions
  • • ViewState per-component, no timers in UI
  • • DB layer trait (SQLite + InMemory)
  • • ChatRequestBuilder (single prologue)
  • • Single tool-orchestrator loop
Skip at birth
  • • 3 databases → 1 SQLite DB
  • • Vector memory (DB1/DB2) → add when needed
  • • Enrichment pipeline → add when needed
  • • Agent orchestration → borrowed pattern only
Borrowed from research
  • • Engine + Config (from Hermes) → fat Rust core, thin config
  • • Streaming agent loop (from Odysseus)
  • • File-based simplicity (FLOWORK V8 lesson)
  • • Mindwalk's adapter interface pattern
  • • Tauri in-process model (no sidecar)
  • • Process groups for lifecycle (lesson 2)

Philosophy & Principles

The motto

Ship the lazy version. Earn the complexity.

Start with one provider, one database, no memory system. Add each only when there's a measurable need. AOTU's 53 bugs came from building ahead of need — dual tool paths, dual summaries, dual stores. One owner. One path. One database.

P1. Engine + Config

Deterministic Rust backend does all the work. Config files define pipeline shape, provider details, model parameters. LLM only does what needs judgment. The engine is testable without the LLM. Source: Hermes / pattern 2

P2. Streaming Agent Loop

Single-user chat is a streaming loop: send prompt → stream tokens → optional tool calls → loop until DONE. The LLM drives the conversation. Tool execution is inline, not async. Source: Odysseus / pattern 4

P3. One Owner, One Path

Every piece of data has exactly one owner at runtime (InteractionRuntime). Every write path has exactly one code path. No mirror stores, no dual loops, no duplicate summaries. Source: AOTU v3

P4. Adapt to grow

The architecture supports growth without rewriting. New providers = new adapter. New data source = new adapter. The Engine doesn't change. File-based state (FLOWORK V8) becomes DB-backed (V2) only when measurable need appears. Source: mindwalk adapter + FLOWORK

Build Order — 8 phases

Every phase produces a working app. No phase depends on the next. Stop any time.

PHASE 0 Scaffold Tauri + Svelte + config
npm create tauri-app
Define AppConfig struct. Load from config.toml.
Single provider entry (NVIDIA). Single model.
PHASE 1 Backend chat + providers Engine + streaming + 4 providers
Build
  • config.rs — load JSON config, models list
  • provider.rs — ProviderAdapter trait + 4 impls
  • request.rs — build HTTP body via adapter
  • response.rs — parse JSON response via adapter
  • stream.rs — SSE line parser + ChatEvent
  • chat_engine.rs — select! loop, 120s timeout
Test
  • cargo test with fake HTTP client
  • Stream timeout test
  • SSE parse edge cases
  • All 4 provider adapter tests
PHASE 2 Database layer Single SQLite DB
Build
  • MessageDb trait: insert, update, get, delete
  • SQLiteMessageDb with migrations
  • InMemoryMessageDb (HashMap) for tests
  • Single messages table (flat, no joins)
  • sessions table (id, name, created_at)
Schema
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY,
  session_id TEXT NOT NULL,
  role TEXT NOT NULL,
  content TEXT DEFAULT '',
  model TEXT,
  created_at TEXT NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);
PHASE 3 Tauri commands Wire everything

commands.rs owns the Tauri wiring:

  • chat_stream → resolve provider → build request → run engine
  • chat_batch → same but batch-mode
  • cancel_request → drop CancellationToken
  • get_sessions / create_session / delete_session
  • get_messages / save_message
PHASE 4 InteractionRuntime Frontend state owner
  • interactions = single $state array
  • start() → creates interaction, calls ChatService
  • appendToAnswer() → streaming from Channel
  • setToolCalls() → switches status to ToolExecuting
  • setDone() → persist to DB
  • setError() → persist error, no summary
  • loadInteractions() → load from DB on init
NOT here
  • ✗ No summary timer
  • ✗ No enrichment
  • ✗ No auto-collapse
  • Just chat + tools. That's it.
PHASE 5 Chat UI Svelte components
  • App.svelte → shell + view routing (chat only at first)
  • Sidebar.svelte → session list + new/rename/delete
  • ChatMessages.svelte → render interactions, auto-scroll
  • ChatForm.svelte → input, send button, model selector
  • Interaction.svelte → one chat bubble (render prompt + response)
PHASE 6 Tool execution UI Frontend tool display

When the interaction status enters ToolExecuting, the UI shows which tools are running, their status (running/done/error), and results. The user sees the tool cycle happen in real time.

  • Connection.svelte — tool call cards inline in chat
  • Status indicator per tool (spinner, checkmark, error)
  • Results expandable on click
PHASE 7 Add complexity on demand Never before

Each feature is a phase that never ships until there's a measurable need. Order by actual user demand:

  1. Session management (rename, search, reorder)
  2. Conversation summary (llmlabel, 1 LLM call)
  3. Memory / RAG (sqlite-vec, similarity search)
  4. Tool workspace (read/write, sandboxed)
  5. Multi-session memory (DB1 + DB2 delta)
  6. Agent orchestration (mailbox + kanban)
  7. Terminal agent streaming (PTY, grid model)

Stop at any point. Each phase adds zero complexity to the previous phases because the Engine doesn't change — only adapters and config grow.

Ownership Rules
  • • InteractionRuntime OWNS interactions[]. Only it writes.
  • • ChatService NEVER owns state. Pure functions.
  • • ViewState is per-component UI chrome, NOT in domain.
  • • DB is a PERSISTENCE COPY, not runtime source of truth.
  • • No timers in components. Ever.
  • • No $state in ChatService. Ever.
What NOT to do
  • • ChatService writing to DB directly
  • • setTimeout in components
  • • Two stores for the same data
  • • Mutating store objects in-place
  • • Passing UI booleans into IPC
  • • ChatService calling Runtime back (circular)

7.1

AppConfig

src-tauri/src/config.rs

LOADED ONCE

Loaded once at startup from a JSON file (AOTU's models.json style). Everything reads from it. No hardcoded values, no duplicate thresholds, no env-var caching in modules.

#[derive(Deserialize, Serialize)]
pub struct AppConfig {
  pub models: Vec<ModelConfig>,
  pub api_keys: HashMap<String, String>,
  pub default_provider: String,
  pub default_model: String,
  pub stream_timeout_secs: u64,
}

pub struct ModelConfig {
  pub name: String,
  pub provider: String,
  pub alias: String,
  pub temperature: f64,
  pub max_tokens: usize,
  // per-provider extras: kwargs, body_extra, reasoning_budget
}
✓ Single source of truth for all models
✓ Loaded once, borrowed everywhere
✓ API keys never logged
✓ JSON format, directly from AOTU data
7.2

Provider

src-tauri/src/provider.rs

ADAPTER SEAM

Four providers from v1 via ProviderAdapter trait. The engine calls adapter.build_request() and adapter.parse_response() — never touches provider-specific formats. Adding a provider = one file, one enum variant.

#[derive(Deserialize, Clone)]
pub enum Provider {
  Nvidia,
  OpenRouter,
  Zen,
  Go,
}

pub trait ProviderAdapter {
  fn endpoint(&self, model: &str) -> String;
  fn build_body(&self, params: &ChatParams) -> Value;
  fn parse_response(&self, body: &Value) -> Result<Answer>;
}
Rules
  • • api_key() reads from AppConfig, not env var
  • • resolve_model(name) -> ModelConfig
  • • Per-provider extras via ModelConfig (kwargs, body_extra, rb)
  • • Engine never imports provider-specific types
7.3

Chat Engine

src-tauri/src/chat_engine.rs

SINGLE LOOP

The select! loop. Owns the SSE stream, parses events, sends ChatEvent variants through the Channel. When tool_calls are detected in the stream, hands off to ToolOrchestrator for inline execution, then resumes streaming the follow-up LLM response.

pub async fn run_stream(
  response: Response,
  channel: &Channel<ChatEvent>,
  cancel: CancellationToken,
  orchestrator: &ToolOrchestrator,
  bundle: &mut RequestBundle,
) -> Result<StreamResult> {
  // select! between:
  // - channel.recv() - parse SSE -> emit ChatEvent
  // - cancel.cancelled() - return StreamResult::Cancelled
  // - 120s timeout - return StreamResult::Timeout
  // On tool_calls: orchestrator.run_cycle(bundle, on_event)
}
✓ 120s timeout · ✓ CancellationToken support · ✓ Inline tool orchestration · ✓ Testable with Vec<Bytes> fake stream
7.4

ToolOrchestrator

src-tauri/src/tool_orchestrator.rs

IN V1

Single tool-execution loop called inline by the streaming engine. Runs tool calls, injects results into bundle.messages, sends follow-up request. Includes CycleDetector for infinite-loop prevention.

pub struct ToolOrchestrator;

impl ToolOrchestrator {
  pub fn run_cycle(
    bundle: &mut RequestBundle,
    registry: &ToolRegistry,
    on_event: Option<&Channel<ChatEvent>>,
  ) -> CycleResult
}

enum CycleResult {
  Continue, Done, MaxTurnsReached, CycleDetected
}
✓ Single max-turns policy
✓ CycleDetector (3 same calls → warning)
✓ Bundle is MUTABLE — results injected
✓ Events emitted for UI via Channel

InteractionRuntime

src/lib/interactionRuntime.ts

SINGLE OWNER

Single owner of all interaction state. No other module holds a $state array of interactions. Every state change goes through this class.

class InteractionRuntime {
  interactions: $state<Interaction[]>
  activeId: $state<string|null>
  error: $state<ChatError|null>

  async start(prompt, route): void
  async cancel(id): void
  appendToAnswer(id, text): void
  setToolCalls(id, calls): void
  setDone(id): void
  setError(id, msg): void
  async load(sessionId): void
}
Rules
  • • interactions is the ONLY $state array
  • • start() is ASYNC — creates immediately (pending)
  • • setToolCalls() → status = ToolExecuting
  • • setDone() → persist to DB async
  • • setError() → persist error, no summary
  • • All DB writes go through DatabaseService
  • • No enrichment, no auto-collapse in v1

Appendix — Research Map

How each source informed AOTUS
0001 — Four Patterns Mailbox+Kanban, Engine+Config, Terminal+Socket, Streaming Loop. Taken: Engine+Config (fat Rust core, thin config) + Streaming Loop (chat UX) + inline tool execution. Deferred: Mailbox+Kanban (multi-agent), Terminal+Socket (agent self-arch)
0002 — Terminal Processes PTY architecture, reader thread vs grid model, process group lifecycle. Taken: CancellationToken + timeout pattern. Deferred: Full PTY control (phase 7+ for agent terminal streaming)
0003 — File vs DB FLOWORK V8 (file-based, running) vs V2 (DB, proposed). Taken: Start file-simple, add DB when needed. .tmp+rename atomicity. Pipeline vs Workflow distinction.
0004 — Desktop Architectures Sidecar (Electron), Local Server (Go), Full-Stack Web (t3). Taken: Tauri in-process model proven correct. Mindwalk's adapter interface. Zustand-level state simplicity.
AOTU archspecV3 53 bug items, 3 deleted files, InteractionRuntime, ViewState, ChatService stateless, DB trait. Taken: All the refactor wins, built in from day one.
